\section{Discussion}

We re-evaluated the rolling-horizon design of \citet{jaffray2026thesis} with two corrections: every
window now starts from the state left by the decisions already implemented, and every run is scored
on its stitched, implemented schedule rather than on a single window's objective. Across
\NRollingRuns\ runs the rolling-horizon configuration has small effects. Almost all configurations
deliver close to the best plan found for their scenario, though \NRunsBeyondFourPct\ of
\NRollingRuns\ runs fall more than 4\% short. Extending the planning window
beyond about four weeks gains little, the 1-day and 7-day re-optimization intervals are
indistinguishable, and only the longest interval (14 days) carries a small, consistent penalty.
Solver time limits explain the failed windows; the weakest simulated-annealing runs had no solver
failure, so configuration matters too.

\subsection{Planning horizon and re-optimization frequency}

The results are consistent with rolling-horizon theory, which predicts a forecast horizon beyond
which further look-ahead does not change the first decisions
\citep{baker1979analytic,sethi1991theory,sahin2008master}. Beyond about four weeks the marginal gain
in delivered volume is within the resolution of the experiment, and at 16 weeks it is slightly
negative. That penalty is confounded with tractability: 16-week windows at 40 blocks are the ones
that most often exhaust the MIP time limit (Table~\ref{tab:windows}). Re-optimization frequency
behaves the same way. The 1-day and 7-day intervals give the same delivered volume, and the 14-day
interval is a little worse, because a longer commitment period leaves less room to correct a plan
that the forecast could not foresee.

\subsection{Why state carry-forward and stitched-plan evaluation matter}

The two corrections change the answer. Without carry-forward, each window restarts from the initial
scenario: it re-plans volume that earlier windows already harvested, rebuilds the inter-phase
inventory from zero so downstream machines wait at every window boundary, and moves machines at no
cost at every boundary. These distortions grow with the number of windows, so they fall hardest on
the shortest lock spans, which is the parameter whose effect is being measured. Scoring a single
window compounds the problem, because a window's objective describes one subproblem, not the
implemented schedule. That combination produced the large re-optimization-frequency effect in
\citet{jaffray2026thesis}; with the state carried forward and the stitched plan scored, the effect
is small. The methodological lesson is general: a rolling-horizon evaluation must carry the
operational state between windows and judge the plan that is actually implemented.

\subsection{Solver choice and tractability}

The largest differences between runs, and all the outright failures, are solver effects. Cold-started
MIP windows reach the time limit in \WindowsStageOneLimitMIPForty\% of the 40-block windows, and where they do, the window may
return no plan or an empty one (Table~\ref{tab:windows}). The simulated annealing never fails,
because it is bounded by iterations rather than time, and it delivered more volume than the MIP in
\NPairsSAWinsAny\ of \NPairsAll\ configurations---in \NPairsSAWinsMIPClean\ of them the MIP
returned a complete plan, so the gap is not only a failure effect. Where the MIP returned a complete
plan it was generally at least as good as the heuristic, but not always. Planning systems at this
scale should therefore not rely on cold-started exact solves alone. Warm-starting the MIP from a heuristic plan, setting a deterministic work limit in
place of a wall-clock limit, or using the heuristic directly for the largest instances are the
practical options \citep{frisk2016detailed,audy2023planning}.

\subsection{Implications for evaluating operational planning systems}
The protocol used here is expressed in terms of the carried state and solver behaviour that any
rolling-horizon planning system shares, so we expect it to transfer beyond FHOPS; we demonstrate it
on one system only, and that is the main limit on its generality.
Four elements make an evaluation trustworthy. First, each window must start from the state implied
by the decisions already locked. For a multi-phase system that means remaining volume, inter-phase
inventory, and machine positions; in other settings it would include open orders, crews, or road
status. Second, the score must be computed on the stitched plan, replayed against the full problem
by an evaluator independent of the solver that produced it. The replay then reveals infeasibilities
that each window's own model cannot see. Third, window outcomes (time limits reached, no solution,
empty plans) must be reported for every run, so that solver failures are not read as planning
effects. Fourth, solver limits should be chosen from the observed trajectory of incumbent and
bound, and reported together with the effective solver effort, because the effort a time limit buys
depends on the hardware and on what else runs on it. These requirements echo the gaps found in
operational planning models more broadly. In the review of \citet{jaffray2026thesis}, none of 23
models reported explicit validation and none released fully open artefacts. A planning system whose
configuration is to be trusted in practice should let users lock decisions, re-plan from the current
state, and audit the implemented schedule, and it should expose these diagnostics. Open scenario
contracts and replayable outputs, as used here, let other groups repeat an evaluation, contest it,
or extend it to their own operations.

\subsection{Practical implications}

For a planner, the practical message is reassuring and simple. Over a season, the choice of
planning horizon and re-optimization interval changes delivered volume by only a few percent, so it
should be made on other grounds: computing cost, how often new information arrives, and how much
schedule change the crews can absorb. A moderate window of four to eight weeks with weekly
re-optimization sits among the best configurations and is far cheaper than daily re-optimization,
because it solves eight to sixteen windows per season instead of 112. Daily re-optimization buys
little when the inputs are deterministic, but it is the natural choice once weather and breakdowns
are in play, which is the case it was designed for. These results refine rather than overturn the
practical guidance of \citet{jaffray2026thesis}: moderate horizons with weekly updates remain a
sound default, but for cost and simplicity rather than because shorter or longer settings would
lose much volume.

The results also support the value of open, reproducible tooling. Because the scenarios, the
runner, and the replay evaluator are all available, the corrections in this paper were possible at
all: the earlier numbers could be reproduced, diagnosed, and replaced. Transparent planning systems
lower the cost of testing counterfactual configurations without operational risk
\citep{de2023perceptions}.

\subsection{Limitations}
This evaluation is deterministic. It isolates the structural effects of the rolling-horizon
configuration and leaves out weather, breakdowns, and forecast error, which are the usual reasons
for re-planning. Extending it with the stochastic playback in FHOPS is the natural next step.

The case studies are semi-synthetic. They use real BC inventory and terrain data but one
harvesting system, synthetic fleets, one landing per block, and no block time windows. They have
no inter-block distances, so machine moves are free and day-to-day continuity and move counts describe
incidental schedule structure, not an optimized property.

The MIP solves are time-limited and not proven optimal, and the full-horizon baselines are not
optimal either (gaps up to 2.2\% on North Island at 7200~s). Relative volume near 1.0 is therefore
close to the resolution of the experiment, and part of the 16-week penalty is a tractability
effect rather than a planning one. The results depend on the solver, the limits, and the host; the
effective Gurobi work rate here was about half the calibrated rate because the host was shared.
Re-running the cold-start MIP arm alone, at a somewhat higher Gurobi work rate, changed the per-run
outcomes (no-solution windows rose from 9 to 32), so the failure counts describe a time-limited run
rather than a fixed property of each instance.
Seeding a window from a heuristic incumbent, made MILP-feasible with a fixed-binary LP, leaves the
typical objective and gap unchanged at equal total budget but guarantees a feasible plan from the
first second; that would remove the no-solution outcome observed in a few of the largest windows.

Simulated annealing used one seed and a fixed iteration budget, so its results show one trajectory
rather than a distribution. The largest runs are expensive: the two 112-day, 1-day-lock runs at 40
blocks (North Island and Prince George) took 56--64~h each, the longest simulated-annealing runs.

\section{Conclusions}

With state carried between rolling-horizon windows and the stitched plan scored against the full
problem, the design of the rolling horizon matters much less than the earlier evaluation suggested.
Across \NRollingRuns\ rolling runs on nine semi-synthetic British Columbia case studies, almost all
configurations delivered close to the best plan found for their scenario
(\NRunsBeyondFourPct\ of \NRollingRuns\ runs fell more than 4\% short). Windowing beyond
about four weeks gained little and was confounded by solver tractability; daily and weekly
re-optimization were indistinguishable, and only a 14-day commitment period carried a small
penalty. The dominant differences were between solvers: cold-started mixed-integer programming
reached its time limit in most 40-block windows and failed outright in a few, whereas simulated
annealing never failed and reached up to \RatioSAMIPMax\ times the MIP volume in those cases. The large re-optimization-frequency
effect reported in Chapter 4 of \citet{jaffray2026thesis} did not survive the corrected procedure;
re-planning each window from the initial state and scoring a single window are the likely causes,
though this design cannot isolate them. Future work should add stochastic
disturbances, test other harvesting systems and regions, and use real operational data.
